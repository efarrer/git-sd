## Newly discovered, fixed
- [x] **`git sd merge --upto <index>` (bottom-prefix / partial merge) + TODO #3 coverage:** `git sd merge` was all-or-"top-mergeable" — it merged the whole ready stack, so there was no way to land just the bottom PR(s) of a set, and TODO #3 (PR0 with a bug-fix sub-commit squash-merged, PR1 then rebases clean) couldn't be driven end-to-end (the sacrificial repo is private on a free plan, so GitHub can't gate merges by review). Added `--upto <index>`: merge only the bottom prefix whose top-level commits' status index is `<= index`. Because the strategy squashes a contiguous bottom prefix, a middle/upper PR can never be cherry-picked — `--upto` only caps where the prefix ends (cannot combine with `--all`). While implementing it, the new tests caught a real bug: `MergePR`'s `--delete-branch` deletes the merged branch, which is the *base* of the first surviving upper PR, so GitHub auto-closed that survivor — fixed by retargeting the first surviving PR onto the base branch before the merge (harmless in a full merge, which has no survivors). Tests: `TestSDMergeUptoRejectsInvalidUsage` (arg validation), `TestSDMergeUptoMergesBottomPrefixLeavingUpperPRs` (3-PR stack, `--upto 1` merges 0-1 and leaves PR2 open+clean), and `TestSDPartialMergeOfSubCommitPRLeavesDownstreamClean` (the full TODO #3 flow: fold bug-fix into PR0, `merge --upto 0`, sync, assert PR1 carries only its own commit). Docs updated (main.go usage, SPEC.md).
- [x] **Integration harness → `go test`, then parallelized:** The ~1900-line custom `cmd/git-sd-test/main.go` harness (one giant `runTests()` with comment-delimited scenarios, sequential, ~468s) was hard to read and run selectively. Converted it to a real `go test` package moved out of `cmd/` to top-level `integration/` (`TestMain` builds the git-sd binary + does one global sanitize + skip-gates on `GIT_SD_TEST_REPO`; helpers and named scenario functions split across files; `go test -run Test<Name>` selectivity; per-scenario PASS/FAIL). Then parallelized: each test clones its OWN copy of the sacrificial repo via `newTestRepo(t)` (`t.TempDir()` + `gh repo clone`), which makes every global mutation clone-local (remote rename, `sd.*` config, `sync`/`cleanup --all`) and — combined with git-sd-id-based branch names being unique per commit — lets 18 top-level `t.Parallel()` tests run concurrently without colliding on the shared GitHub remote. The `feat-a` lifecycle stays one test (ordered `t.Run` sub-steps) since its steps share state; the two semi-coupled scenarios (MultipleStackSetsIsolation, CrossSetBaseChaining) were reworked to create their own coexisting sets. Results (Makefile default `-parallel 4`): 468s → **159s (2.9×)**; `-parallel 8` → 131s (3.6×), both green with no GitHub rate-limit errors. Splitting `feat-a` further was measured as not worthwhile (wall time is bound by aggregate load, not the feat-a pole). Converting to clean per-test clones also exposed and fixed a latent ordering bug: `HierarchicalIndexing`/`MoveToSubIndex` were bundled after `Merging` (which, since B-013, actually merges feat-a and drops its commits), so in an isolated clone they had no commits — split out into their own self-contained tests.
- [x] **PR identity keyed by mutable index; sub-commit grouping unimplemented:** Reproducing a "2-commit stack → bug-fix sub-commit on commit 1 → sync → squash-merge PR1 → clean PR2" workflow against the real repo showed it broken at the root: PR branch names came from `FormatBranchName(stackSet, index)` using the *physical* index, so any index shift (adding a sub-commit, reordering, a partial merge) renamed a PR's branch and orphaned it — a sub-commit hijacked commit2's branch/PR, commit2 was orphaned with no PR, and after a partial merge PR2 kept showing the merged commit's files. Sub-commits (SPEC.md:46/47/80) were also never grouped into their parent's PR (`SubIndex` was display-only). Additionally `assign` never set the index, so `sync` without an intervening `status` collided every commit at index 0. — Reworked identity around the stable `git-sd-id`: new `cmd/git-sd/groups.go` (`GroupCommits`) folds each top-level commit + its sub-commits into one `PRGroup`; `FormatBranchName` now takes the top-level commit's git-sd-id (default format `sd/{user}/{stack-set-name}/{git-sd-id}`, new `{git-sd-id}` placeholder); `sync` creates one PR per group (sub-commits fold into the parent's branch, one PR); `merge` squashes a group (top-level + sub-commits), and — since it performed the squash — drops the merged commits from the local branch afterward (`git fetch` + `git.RebuildCommitChain` onto the updated base), leaving the downstream stack clean; `cleanup` deletes branches by git-sd-id; `move src:X.Y` now joins the moved commit to its parent's Stack Set. The index-collision and stale-branch bugs disappear because identity no longer depends on the index. Added a "Sub-commit Folding" + "Sub-commit Squash-Merge + Local Drop" integration scenario (the full 2-PR partial merge can't be driven to a successful `git sd merge` on the sacrificial repo — GitHub forbids self-approving a multi-PR stack — so the squash-merge + local-drop is exercised with a single-PR group). Updated the Custom Branch Name Format scenario to a `{git-sd-id}` format.
- **Migration:** branch identity changed from index to git-sd-id, so branches created by the old scheme aren't recognized after upgrading. Re-sync (creates git-sd-id-named branches) and delete stale `sd/*` branches once; this is a pre-release break with no automated migration.
- [x] **Hardcoded `.git/` path broke worktrees:** `metadata.getMetadataPath` returned the relative literal `.git/sd/metadata.json`, which fails with `ENOTDIR` ("not a directory") inside a linked git worktree — there `.git` is a *file* (`gitdir: .../worktrees/<name>`), not a directory — so every subcommand errored with `open .git/sd/metadata.json: not a directory`. It also silently misbehaved when git-sd was run from any subdirectory rather than the repo root. — Fixed by resolving the real git dir via `git rev-parse --absolute-git-dir` and joining `sd/metadata.json` onto it, giving per-worktree isolated metadata (each worktree under its own `.git/worktrees/<name>/sd/`, so `cleanup --all`/`merge --all` in one worktree never touch another's stacks) and correct behavior from any subdirectory. Added a permanent "Worktree Metadata" scenario in `cmd/git-sd-test/main.go` (`runWorktreeChecks`) that creates a linked worktree and exercises every metadata-touching command from inside it — `status` (the exact ENOTDIR repro), `move` (reorders two commits), and a full `assign`/`sync`/`merge`/`cleanup` cycle — then asserts the metadata lands in the worktree's own git dir, distinct from the primary checkout's.
- [x] **Removed hardcoded `"origin"` remote assumption:** `internal/github.PushBranch`/`DeleteRemoteBranch` hardcoded the literal `git push origin ...`/`git push origin --delete ...`, regardless of what `sd.base-branch` was configured to (which itself used to require the remote portion to literally be `origin`, per the entry below). — Replaced `git.ValidateBaseBranch`'s origin-only check with `git.ParseBaseBranch` (pure format check) plus `git.ListRemotes`/`resolveRemote` (validates the remote is genuinely configured, whatever it's named), and threaded the resolved remote through `PushBranch`/`DeleteRemoteBranch` (`sync.go`, `merge.go`, `cleanup.go` — `cleanup.go` didn't read `sd.base-branch` at all before this, via the new `git.BaseBranchRemote()`). Also replaced the previous literal `"origin/main"` default with a deterministic tiered rule (`configuredBaseBranch`): prefer an `origin` remote if one exists, else the sole configured remote if there's exactly one, else refuse to guess and ask for `sd.base-branch` explicitly.
