# Stacked Diff CLI Tool (git-sd) - Design

## Architecture & Design
- **Command Name:** `git-sd`.
- **Git Integration:** Subcommand `git sd`.
- **Metadata:** Stored in `.git/sd/metadata.json` to prevent cross-checkout conflicts.
- **Integration Test Tool:** Separate tool that calls `git-sd`.

## Implementation Details

### Go Implementation
- **Project Structure:**
    - `cmd/git-sd`: Entry point for the CLI tool.
    - `integration`: The `go test` integration suite (`go test ./integration/`).
    - `internal/git`: Low-level git command wrappers.
    - `internal/github`: GitHub CLI (`gh`) wrappers and API interactions.
    - `internal/metadata`: Logic for reading and writing `.git/sd/metadata.json`.
    - `internal/ui`: Terminal UI and formatting logic (emojis, tables).
- **Trailer Management:**
    - `AddTrailer` uses `git interpret-trailers --where end --if-exists replace --trailer git-sd-id=<id>` to append or update the `git-sd-id`.
    - **ID Generation:** `git-sd-id` is a 5-character alphanumeric hash (e.g., `s3f2a`). It is generated for a commit lacking one by `git sd assign`, `git sd move` or `git sd fixup`, each of which tags every untracked commit in range before acting (`git.RewriteCommitsWithIDs`); there is no separate command, and the other commands skip a commit without an id.
    - The existing commit message is passed via **stdin**.
    - The resulting message is used with `git commit-tree` to create the new commit.
- **GitHub CLI access (`internal/github/gh.go`):** every `gh` invocation goes through one wrapper (`ghOutput` / `ghCombined`), and a boundary test fails the build if `exec.Command("gh"` appears anywhere else or a `git push` appears outside `PushBranch`. The wrapper checks `exec.LookPath("gh")` once (`sync.Once`), runs the command, and translates failures into the two `EnvError` messages: exit code 4 (gh's "authentication required"), or output containing `HTTP 401`, `Bad credentials` or `gh auth login`, means not authenticated; other failures are returned unchanged. Process-wide state (safe for concurrent use) records `verified` once any call succeeds and caches a definite environment failure so later calls return it without spawning `gh`; transient errors are never cached. There is deliberately no startup check and no per-command table of which commands need `gh`: `PushBranch` calls `ensureReady()` (a `sync.Once` around one real `gh api user` call, skipped if already `verified`) because it is the one place a command pushes before its first `gh` call. `git.AuthHint` appends a hint to git's own error text for `git push` / `git fetch` auth failures. A cheap local proxy such as `gh auth token` is not used: it can succeed where `gh pr view` reports authentication required. The startup `gh auth status` this design replaced cost about 0.4 s (a network round trip) on every command, including ones that never touch GitHub, which is why there is no startup check.
- **Conflict Handling:**
    - `move`/`fixup` rebuild the chain with `git rebase -i` (todo of `pick` lines in the new order, supplied via `GIT_SEQUENCE_EDITOR`; `--no-autosquash --empty=keep`). On conflict the tool leaves that rebase in progress, so plain `git rebase --continue` replays the rest and `--abort` restores the original branch. A cherry-pick loop can't do this: `--continue` would not replay the remaining commits and `--abort` would stop at a partial chain.
    - `rebase` also rebuilds with `git rebase -i --onto <base> <merge-base>` (todo of the remaining `pick`s, `--empty=drop` so a pick already upstream is dropped as landed), and leaves that rebase in progress on conflict. Before starting it takes a backup (see "Rebase Strategy"); `--abort` discards that backup, `--continue`/`--skip` keep it so `rebase --rollback` still works.
    - **Pending move:** `metadata.json` may hold a `pending_move` (`old_order`, `new_order`, `moved_id`, and the `parent_id`/`sub_rank`/`stack_set` to apply). `move`/`fixup` save it before starting the rebase and clear it on success. Every `git sd` command reconciles it on startup: rebase still in progress -> leave it (and refuse mutating commands); id order equals `new_order` -> apply and clear; equals `old_order` (abort, or a crash before the rebase started) -> drop; neither -> drop with a warning. It is not part of rebase backups.
    - **Pending rebase:** `metadata.json` may hold a `pending_rebase` (`orig_head`, `target_tip`, `retire_ids`, `drop_ids`, `backup_ref`). `rebase` saves it before starting and clears it when the rebase finishes without stopping. Every `git sd` command reconciles it on startup: rebase still in progress -> leave it (and refuse mutating commands); otherwise the rebase was continued iff `HEAD != orig_head`, `target_tip` is an ancestor of `HEAD`, and none of `drop_ids` is still in local history -> retire `retire_ids` plus every tracked commit now absent from history (the usual retirement tail); otherwise it was aborted (or never started) -> delete the backup named by `backup_ref` and drop the record. A vanished commit whose PR is still open is neither retired nor has its branch queued for deletion (that would close the PR); a warning names it. It is not part of rebase backups.

### Metadata Schema (`metadata.json`)
The metadata file tracks the relationship between `git-sd-id`s and their assigned Stack Sets.
- **Source of Truth:** While metadata stores `index`, `parent_id`, and `sub_rank`, the physical order of commits on the branch (relative to the base branch) is the absolute source of truth.
- **Entries exist only for commits with something to remember.** An entry for a commit that is tracked but not assigned to a Stack Set (Ready) records nothing: with no entry `status` shows the commit as Ready, `GroupCommits` leaves it ungrouped, and `assign` creates the entry on demand. Such *blank* entries (no stack set, parent, PR, branch or sync record; `CommitMetadata.IsBlank`) are therefore never created by `status` (it refreshes `index` only on entries that already exist) and are dropped on every save (`Metadata.PruneBlank`, called by `Save`), except one that a sub-commit names as its `parent_id`. This heals a `metadata.json` written by older versions, whose `status` created a blank entry for every Ready commit and never removed it (B-022); backups no longer copy blank entries either. Entries that DO carry information are never dropped here: an assigned commit that has left the branch is retired by `rebase` (after checking its PR), not pruned.
- **Index Synchronization:** Every time `git sd status`, `assign`, or `sync` is run, the tool walks the commit log. It identifies all commits belonging to a Stack Set and re-calculates/updates their `index` based on physical sequence. This ensures that manual `git rebase -i` operations are reflected in the tool.
- **Status PR lookups:** `git sd status` looks up each assigned commit's PR state (`gh pr view`, ~0.4 s per call) concurrently, bounded by `maxConcurrentPRLookups` (8), instead of one after another, so its cost is about one round trip for any stack of up to 8 PRs rather than growing with the stack. A failed lookup shows the Unknown marker (❓), never a guessed state. Every marker (icon, word, color, legend text) is one row of the table in `internal/ui/marker.go`, which is the single source of truth: `--legend` is generated from it, and tests check that SPEC.md's and `sd-sim.sh`'s legends match the program's and that every marker is either produced by code or on an explicit not-yet-implemented list. Syncing comes from a small lock file, `<git dir>/sd/operation.json` (`cmd/git-sd/operation.go`): `sync` and `merge` write `{command, pid, set, started}` when they start (after their arguments are validated) and remove it when they finish, through `exitCleanly` on the `os.Exit` paths and a `defer` on normal return, and only if the file still carries their own PID. `status` (`activeOperation`) trusts it only while that PID is alive (a signal-0 check), it is under two hours old and it parses; anything else is a stale lock from a killed or crashed run, which is ignored and removed, so a lost cleanup can never leave 🔄 showing. An empty `set` means every set. The marker applies to the assigned top-level commits of the affected sets, ranks below Merged, Closed and Unknown (`withOperation`), and is purely local: no network call. While an operation is active `status` skips its own `metadata.json` save (a `status` that finished after the operation's final save would otherwise overwrite the PR numbers the operation just recorded), and if the branch looks empty it adds a note, because building a PR's branch (`BuildTrailerStrippedChain`) checks out the base commit for a moment. Two operations running at once just overwrite each other's file; that is not guarded, as the commands already assume one at a time. Conflict comes from two more fields of the same `gh pr view`: `mergeable` is `CONFLICTING` or `mergeStateStatus` is `DIRTY` (`github.DetailedPRInfo.HasConflict()`); `UNKNOWN` (GitHub still computing) counts as no conflict. Base mismatch is deliberately not part of it: it is legitimate between a `rebase` and the next `sync`. CI states come from the `statusCheckRollup` that the same `gh pr view` already returns (no extra call): `github.DetailedPRInfo.CIStatus()` reads its `CheckRun` entries (`status`, `conclusion`) and `StatusContext` entries (`state`) and reports failing if any entry failed, else running if any is unfinished, else none. A check run counts as failed for the conclusions FAILURE, TIMED_OUT, STARTUP_FAILURE and ACTION_REQUIRED; CANCELLED (usually a superseded run), SKIPPED, NEUTRAL and STALE count as neither, and a rollup that can't be parsed counts as no CI information rather than a guess. The marker is chosen by `classifyPR` (`cmd/git-sd/status.go`) from the same `gh pr view` fields (`state`, `reviewDecision`, `isDraft`): Merged/Closed first, then Changes Requested, Draft, and otherwise Approved when `reviewDecision` is `APPROVED` and Review for anything else (including an empty decision, which is what GitHub returns for an unreviewed PR in a repo that does not require reviews). A commit with no PR is Assigned (`prMarkerID`). `status` prints the legend (when requested) before any repository lookup, so it works with no commits and with an unresolvable base branch; `legendRequested` decides. `status` builds each row as a map of column name to cell and renders only the columns `sd.status.columns` selects (`statusColumns` validates the names, case-insensitively and ignoring spaces/hyphens; `Icon` has a blank header); a sub-commit's row has a blank Icon/Status and an indented Message, because its PR is its parent's and that state is already on the parent's row; the only marker it can show is `Unsynced` (`subCommitMarker`): the parent has a PR (not merged or closed) and the sub-commit isn't recorded as pushed into it. `sync` records, for every commit of a group it pushed whose PR exists, `synced_fingerprint` (a short sha256 of the commit's `git patch-id --stable` plus its message with the `git-sd-id` trailer stripped, so a rebase that leaves the diff alone does not count as a change but a reword does) and `synced_pr` (the PR number it went into); `status` recomputes the fingerprints and compares both, so attaching, amending, rewording or moving a sub-commit into another PR shows `Unsynced` until the next sync. Patch-ids come from ONE `git log -p --no-merges | git patch-id --stable` pipeline over the range (`git.PatchIDs`), run by `status` only when some sub-commit's parent has a PR. Known limits: reordering sub-commits inside the same PR is not detected (same patch-ids); a sub-commit from before this record existed shows `Unsynced` once, until the first sync after upgrading; top-level commits are recorded too but their rows don't use it yet. The Status word is colored by `ui.Colorize` with the marker's color from the marker table, only when `ui.ColorEnabled` says so: `sd.status.color` is not `false`, `NO_COLOR` is unset or empty, `TERM` is not `dumb`, and standard output is a terminal (`ui.StdoutIsTerminal`, a character-device check). Piped output never carries escape sequences. Tables are aligned by terminal display width (`ui.DisplayWidth`: emoji are 2 columns, ANSI escapes and variation selectors 0), not by byte or rune count.

- **`pending_branch_deletions`** (list of `{branch, stack_set}`) and **`rebase_backups`** (list of backup snapshots) are both omitted when empty, as are **`pending_move`** and **`pending_rebase`** (in-flight conflict records, see "Conflict Handling"); see "Sync Strategy" and "Rebase Strategy" below.
- **Sub-commit representation (`ParentID`/`SubRank`):** a commit is a sub-commit iff `parent_id` is non-empty, naming its top-level parent's own `git-sd-id` — an explicit reference, not inferred from physical adjacency (the source of several bugs in an earlier design that tried to infer parentage from commit order + matching Stack Set name). `sub_rank` orders a sub-commit among its siblings for display (`<parent's current index>.<sub_rank>`, e.g. `"1.1"`) and for computing where a new one should be physically inserted; it's meaningless on a top-level commit (`parent_id == ""`), which is always `""`.
  - `sub_rank` is a **decimal-digit string** (`"1"`, `"45"`, `"91"`), not a small integer — read as the digits after `0.`, e.g. `"45"` means rank 0.45. This lets a new sub-commit be inserted between existing siblings without renumbering anything (the same technique used for reorderable-list "rank" fields in tools like Trello/Notion). A digit string rather than a `float64` sidesteps floating-point rounding artifacts (no `0.30000000000000004`).
  - **Comparison:** two ranks compare by right-padding the shorter digit string with `"0"` to equal length, then comparing as integers (`"1"`→`"10"` vs `"15"` → `10 < 15`, i.e. `0.1 < 0.15`).
  - **Auto-rank algorithm** (`git sd fixup`): let `maxRank` be the largest existing rank among the target's sub-commits (`"0"` if none) and `d` its digit length. If `maxRank` isn't all-`9`s at length `d`, the next rank is `maxRank + 1` rendered at that same length (`"1"`→`"2"`, `"8"`→`"9"`). If it is (the tier is full), widen by one digit first (`"9"`→`"90"`, `"99"`→`"990"`) then `+1` (→`"91"`, `"991"`). This gives 9 fixups at the coarse (0.1–0.9) tier and 90 more before a third digit is needed.
  - **Grouping:** `GroupCommits` (`cmd/git-sd/groups.go`) walks commits in physical order and assigns each to a PR group by `parent_id` lookup, not by re-deriving parentage from adjacency — a sub-commit whose `parent_id` doesn't resolve to a top-level commit that itself has an open group (missing metadata, or a dormant/unassigned parent) is excluded from grouping entirely, never silently promoted to its own group.
  - **Note on `StackSetMetadata`:** the schema has no `registered_prs` field (an earlier version of this doc showed one) — the ordered PR list for `CreateStack` is derived fresh from `GroupCommits`'s output each time, not stored.

### Sync Strategy (Three-Pass)
- `git sd sync` ensures all PR metadata and GitHub Stack registration are current:
    1. **Pass 0: Dissolve finished sets; keep live Stacks unless they must change:** Pass 0 iterates `StackSets` entries (not the set names derived from commits), so a set whose commits have all been retired is still seen: it is unstacked and, since no commit references it any more, dissolved — its `StackSets` entry is deleted and it gets no Pass 1/2 work. A set that still has commits keeps its registered Stack: its current PR list is read (`github.GetStack`, `GET /stacks/{n}`) in the same concurrent round trip as the PR-state prefetch, and the Stack is unstacked *lazily*, only just before something GitHub would reject: confirmed hands-on, GitHub rejects any `--base` on `gh pr edit` for a PR that's part of a registered Stack ("Cannot change the base branch because the pull request is part of a stack"), even the value it already has, but accepts title/body edits and force-pushes of the PR branches, and a Stack that was never unstacked still merges (verified 2026-10-10 on a rebuilt, force-pushed chain). So `sync` sends `--base` only when the PR's live base (`baseRefName` from the prefetch) differs from the one the chain gives it, and unstacks the set first in that case; it also unstacks in Pass 2 when the registered list no longer equals the wanted one. If the Stack can't be read (any error), the set is unstacked up front, exactly as before. Net effect: a re-sync with nothing changed, after an amend, or after a title/body edit leaves the Stack alone (saves the unstack and re-register calls, ~2.2 s); a reorder, insert, removal, new PR or partial merge still tears down and re-registers.
    2. **Pass 1: Push & PR Creation/Update:**
        - Cherry-picks each group's own commits onto the chain's current tip, stripping each one's `git-sd-id` trailer (see "Trailer transparency" below).
        - Pushes the resulting branch to remote.
        - Creates or updates PRs to obtain/confirm `pr_url` and `pr_number`; the PR body is just the commit's own (trailer-stripped) message body.
    3. **Pending remote branch deletions:** after Pass 1 has retargeted every surviving PR, each queued `pending_branch_deletions` entry in scope is deleted from the remote (a failed deletion stays queued with a warning). Deletion is deferred to this point, rather than done when a commit is retired, because deleting a branch that an open PR is still based on makes GitHub close that PR — Pass 1 is what moves such PRs onto the base branch first. Pass 1 can fail to retarget (a push or base-edit error only skips that group), a closed PR's dependents are never retargeted by GitHub itself, and PRs outside git-sd can target the branch too, so before each deletion sync asks GitHub directly (`internal/github.OpenPRsBasedOn`, i.e. `gh pr list --base <branch> --state open`). Any open dependent, or a failed lookup, keeps the branch queued with a warning (fail safe).
    4. **Pass 2: Register Stack** (confirmed on real GitHub: registering a chain with a missing PR, e.g. [A, C] when B's create failed, is refused with `422 Pull requests must form a stack, where each PR's base ref is the previous PR's head ref`, so a set is skipped here while any of its live groups has no PR, and the one real error — the failed create — is the only one reported; the next sync creates the PR and registers all of them, verified end to end by `TestSDSyncRecoversFromAFailedPRCreateOnGitHub`): if the set's registered Stack was kept and its PR list already equals the set's current ordered PR-number list, nothing is done; otherwise the set is unstacked (if it still is registered) and `CreateStack` is called with the current list. GitHub's Stacks API rejects registering fewer than 2 PRs (a lone PR isn't a stack — confirmed hands-on via a 422 "2 items required; only 1 was supplied"), so a set with 0-1 PRs is simply left unregistered; git-sd's own PR is sufficient on its own.

### Rebase Strategy (Content-Aware Upstream Reconciliation)
- `git sd rebase` (`cmd/git-sd/rebase.go`) replaces the former `cleanup` command's local half. It is strictly local; all remote teardown lives in `sync` (see above).
- **Landed detection:** for each group whose PR is `MERGED`, `internal/github.GetPRInfo` also returns `mergeCommit.oid`. The PR's merge commit must be an ancestor of the freshly fetched base; otherwise it's a mismatch and the command aborts. The PR's own `baseRefName` is deliberately not checked: in GitHub's cascading stack merge, every PR above the bottom one keeps its lower PR's branch as its base even after it lands on the base branch, so `baseRefName` says nothing about whether the content landed.
- **Content classification (`cmd/git-sd/landed.go`, `classifyLanded`):** the group's own commits are replayed onto a candidate "before" commit with `merge-tree` plumbing (`internal/git.SimulateChainTree`), giving the local net tree `L`; candidates are `mergeCommit^1` (squash and merge-commit merges, which GitHub does not distinguish in the API) then `mergeCommit~N`, N = the group's commit count (rebase-merge). If `L` equals the merge commit's tree `U`, the group landed exactly. Otherwise the first candidate whose replay is clean is used for a three-way merge `merge(base=before, ours=U, theirs=L)` (`internal/git.MergeTrees`: `git merge-tree --write-tree` on git >= 2.38; otherwise `read-tree -m --aggressive` plus a per-file `merge-file` pass, because read-tree alone is file-level and would report a conflict whenever both sides touched the same file): result `== U` -> landed (identical, or upstream has more); clean but `!= U` -> *delta* (local has extra changes); conflict -> *conflict* (git's merge treats overlapping non-identical hunks as conflicts, so a local change that extends a landed change onto an adjacent line is a conflict, not a delta; the user then resolves it in the rebase). Replaying the group's commits (rather than diffing a range of the local branch) matters because a group's commits need not be contiguous — sub-commits and interleaved Stack Sets can sit between them (cf. B-012: never shortcut content comparison). If no candidate replays cleanly the group cannot be classified and the command aborts.
- **Follow-up commits:** a delta or conflict group is dropped from the rebase todo and replaced, at the position of the group's first commit, by one synthetic commit built with `commit-tree` (author of the group's top commit, a fresh `git-sd-id`, message `Follow-up to PR #N: <subject>` plus a body listing the original commits). Delta: tree = the merge result, parent = the merge commit, so its diff is exactly the delta and landed lines are not replayed against later upstream changes. Conflict: tree = `L`, parent = the "before" commit, so replaying it onto the new base surfaces the real conflict. `pending_rebase` records each synthetic (`id`, `stack_set`, `note`); once the rebase finishes, every synthetic still in history is registered under its Stack Set (assigned, no PR) and its note printed; one that was skipped or resolved to empty vanishes and nothing is registered. The conflict stop message names the PR, lists the conflicting files and translates ours/theirs (during a rebase `ours` is the updated base and `theirs` is the local commit); it warns that `git checkout --ours/--theirs <file>` takes that side's WHOLE file, so editing the conflict markers is how to keep one side of a single hunk.
- **Backups:** `metadata.json` holds `rebase_backups`, a list (oldest first, capped at 10) of `{sha, ref, commits, stack_sets, pending_branch_deletions, timestamp}`; each entry also has a `refs/sd/backups/<unix-nanos>` ref pinning `sha`, so the backed-up commits stay reachable regardless of reflog/gc settings or worktree removal. A snapshot is taken in memory before any mutation and persisted before the rebuild starts. `--rollback` resets `HEAD` and restores all three metadata fields from the same entry together, then drops the entry and its ref; restoring git without metadata (or the reverse) would orphan commits. Backups are verbatim snapshots of the state before a rebase, which is what makes `--rollback` exact, so they deliberately keep entries that the live `commits` map no longer has: PRs that have since merged, and (for snapshots taken before B-022) blank entries for unassigned commits. They are not rewritten by the pruning that keeps the live map clean; they simply age out under the 10-backup cap.
- **Conflicts:** a conflict leaves a standard `git rebase` in progress (see "Conflict Handling") rather than rolling back automatically; the backup taken first remains available through `rebase --rollback` after a continued rebase and is deleted on abort.
- **Retirement (B-018 invariant carried over from `cleanup`):** a commit is retired only if it was in a dropped (landed) group, in a `CLOSED` group, or has metadata but is absent from local history after the rebuild. "Present" is judged over *every* commit in range, not just grouped ones, so a dormant sub-commit isn't mistaken for landed. Retiring deletes the metadata entry and local branch and queues `{branch, stack_set}` in `pending_branch_deletions` for `sync`.
- `git sd merge` is GitHub-only and does not use this core: it never touches the local branch or working tree. The merged groups are dropped (and their metadata retired) by a following `git sd rebase`, which verifies their content landed first. `merge` leaves the Stack Set's metadata entry in place for `sync`'s Pass 0 to dissolve once every commit in it has been retired.

### Merge Strategy (Native Async Stack Merge)
- `git sd merge`:
    1. Identifies the top-most PR at or below `--upto`'s cap (or the top of the stack if `--upto` is omitted); every group at or below it must already have a PR.
    2. Submits that PR to GitHub's async stack-merge API (`PUT /pulls/{n}/merge-async`, polled via `GET /pulls/{n}/merge-async/{uuid}`), which merges every PR in the stack up to and including it, atomically, with branch protection as the sole approval/CI gate. `merge` waits up to 5 minutes for the async merge to finish (polling every 0.5 s, backing off to 2 s), because GitHub documents a stack merge can take "a few minutes" and a shorter cap made `merge` report a merge as unfinished while GitHub was still working; if it is still pending after that, `merge` stops waiting with an error telling the user to check the PR (the merge itself continues on GitHub).
    3. Each merged PR lands on the base branch as its own commit, with every PR above it server-side rebased onto the new base — there is no squashing and no closing/redirecting of "superseded" PRs, since every PR in the range genuinely merges as itself.

## GitHub Stacks Backend

### Background
GitHub shipped native "Stacked Pull Requests" as a public preview REST API plus a `gh stack` CLI extension (2026-07-30). It solves, at the platform level, exactly the problems git-sd used to hand-roll in `internal/github` and `cmd/git-sd/merge.go`: merging a PR mid-stack automatically retargets/rebases the PRs above it, and merges are driven through a dedicated async API that structurally avoids the "not mergeable" transient race behind B-013/B-014/the survivor-close bug. This was confirmed hands-on against the sacrificial repo — a real stack was created, a bottom PR was merged, and the surviving PR's branch ref was verified (via `git merge-base --is-ancestor`) to have been genuinely rebased onto the new base server-side, not just cosmetically retargeted in the UI. The REST endpoint shapes below are documented at `docs.github.com/en/rest/pulls/stacks` and the async-merge reference at `github.github.com/gh-stack/reference/merge-api`.

git-sd's user-facing interface is unaffected by this backend: the single linear working branch, `git-sd-id` commit-trailer identity, and the `assign`/`move`/`fixup`/`status`/`sync`/`merge` command surface all stay exactly as they were before (`cleanup` was later replaced by `rebase` + `sync`). This was a backend swap — git-sd keeps owning the commit-level model and delegates PR/stack lifecycle and merging to GitHub's native Stacks feature instead of driving `gh pr create`/`edit`/`merge` directly.

### REST surface used
- `POST /repos/{owner}/{repo}/stacks` with `{"pull_requests": [n, ...]}` (bottom to top; each PR's base ref must already match the previous PR's head ref; **requires at least 2 PRs**, confirmed hands-on) — `internal/github.CreateStack`.
- `POST /repos/{owner}/{repo}/stacks/{stack_number}/unstack` — `internal/github.Unstack`; PRs that are merged, merging, or queued for merge are left in place rather than erroring on a partial dissolve. When EVERY PR in the Stack is already merged (the usual state of a set that `merge` finished and `rebase` retired) GitHub answers HTTP 422 `Pull requests #… cannot be removed from this stack`; `Unstack` treats that one response as success — there is nothing left to unstack — so the finished set is dissolved instead of being reported as an error (which `sync`'s exit status would otherwise turn into a failure). Any other error is still an error. (The Stacks API also documents a `.../stacks/{stack_number}/add` "extend" endpoint for appending PRs without a full teardown; git-sd doesn't use it — see Pass 0 above, every sync unstacks unconditionally rather than trying to detect the narrower "pure append" case.)
- `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge-async` (with `merge_method=squash`, matching the pre-migration `gh pr merge --squash` behavior for folding a PR's own sub-commits) then `GET .../merge-async/{uuid}` until the status leaves `pending` — `internal/github.MergeStack`. A 404 on submit means the repo/token lacks access to this endpoint even where the rest of the Stacks API works; surfaced as `github.ErrAsyncMergeUnavailable` rather than a confusing generic failure, with no fallback to a legacy merge path.
- All calls go through `gh api` (not the `gh-stack` CLI extension) — this doubles as the long-pending "Direct API Integration" item in TASKS.md.

### What changed from the `gh pr`-driven prototype
- **Restructuring (`move`/reassign):** the Stacks API has no reorder endpoint, and — confirmed hands-on — flatly refuses to let a stack-registered PR's base be edited at all (`"Cannot change the base branch because the pull request is part of a stack"`). A restructure is therefore handled as tear-down-and-rebuild: before Pass 1 issues an `UpdatePR` that changes a base (a restructure, or a partial-merge retarget-to-`main`), `sync` `Unstack`s the set's existing registration, so that call is free to succeed; Pass 2 then `CreateStack`s fresh with the current ordered PR-number list. A partial merge (`--upto`) leaves the survivors' `StackSetMetadata` (and its `StackNumber`) in place rather than deleting it, specifically so the next sync knows there's still a registration to read and, if the survivors' list no longer matches, to tear down.
- **Timing (`GIT_SD_TIMING=1`, `internal/timing`):** a diagnostic for `status` latency. `timing.Phase(name)` brackets the phases of `buildStatusView`; `timing.Spawn("gh")` is called around the `gh` wrapper (`ghRun`, the single place every `gh` call goes through). Every `git` process is counted without touching its roughly sixty `exec.Command` sites: with timing on, `internal/timing` sets `GIT_TRACE2_EVENT` to a temporary file in its own environment (children inherit it) and `Report` reads it back, taking one `cmd_name` and one `exit` (with its elapsed time) per top-level process, keyed by the event's session id so concurrent processes don't mix. That also counts the `git` processes `gh` starts. Every command prints the report: `main` does when a command returns and `exitCleanly` before it exits (all the commands' exits go through it). Off, every hook is a no-op.
- **Notifications (`cmd/git-sd/notifytest.go`, `watch.go`):** the variables `sd.watch.notify-command` receives are listed once, in `notifyVariables`; `eventEnv` (one per PR change) and `messageEnv` (the offline notice) build the environment, and a test fails if they set anything the table does not list or omit anything it does. `git sd notify-test` builds a sample `watchEvent` and passes it through the same `eventKind`/`eventTitle`/`eventMessage`/`eventEnv` functions `watch` uses, then runs the configured command with `runNotifyCommandCapture` (like `runNotifyCommand`, but returns the output so the test can show it). `--agent`, `notify-test` and the manual (`manual.go`, printed by `git sd help` / `git-sd --help`; there is no man page, since `git sd --help` is handled by git, which looks for one, so the manual is reached through `help`) print or are checked against that same table and the `notifyEventKinds` list (every value `eventKind` can return), so the documentation cannot drift from the code. A test also fails if the usage text, `--agent` text or manual mention SPEC.md, DESIGN.md, TASKS.md or BUGS.md: the installed tool must be documented by itself.
- **Watch link (`cmd/git-sd/watchlink.go`):** one file, `<git dir>/sd/watch.pid` (per worktree, like the metadata), is both a lock and a doorbell. Lock: `acquireWatch` creates it with its content (`{pid, started}`) already in place, as a temporary file hard-linked into position (atomic, and it refuses to replace; an exclusive create where links are unsupported), so two watches starting together cannot both win and a reader never sees a half-written file. If the file exists and its process is alive (and the record is under 7 days old, for pid reuse) the new watch refuses with the pid, the start time and the path to remove; a record that is missing, empty, unparseable, dead or too old is as good as none and is taken over at once. `releaseWatch` removes it only if it is still this process's record. Doorbell: its modification time. `touchWatch` (a `Chtimes`: it writes nothing and creates nothing, so a touch that arrives just after the watch stopped and removed its file is a harmless no-op) is called by `status` and, through `ringBy`/`ringWatch` (set in `main`, run by its defer and by `exitCleanly`, so every exit path rings), by the mutating commands (`track`, `assign`, `move`, `fixup`, `sync`, `merge`, `rebase`), each only when `liveWatch` is true. `watch` runs a `ringFeed`: `sleepWall`'s once-a-second tick stats `watch.pid` (one syscall; two touches inside one coarse mtime tick count as one), and a change ends the sleep early; the loop then polls exactly as it would at the end of its interval, except that the schedule is left alone: if the poll finds no change `holdWatchInterval` keeps the current wait (it neither doubles nor resets to the minimum, so running `status` while the watch is at 60 s does not drop it to 5 s), and a change restarts the wait at the minimum as usual. There is deliberately no payload: the watch does not adopt what `status` showed, so it may announce a change `status` has just displayed (a harmless duplicate, chosen over a second file and the read-modify-write races that come with it, and over a silent refresh, which could swallow a change that happened in the gap). `watch` itself never touches the file, so it cannot ring itself.
- **Watching (`git sd watch`, `cmd/git-sd/watch.go`):** (a PR that disappears from the view between two polls, e.g. after `rebase`, would otherwise cost the user a merge notification: `missedEndings` looks each such PR up once through `watcher.lookup` (`getDetailedPRInfo` + `classifyPR`) unless its last known marker was already Merged or Closed, and turns a Merged or Closed answer into a normal event from the last known state, labelled from the last snapshot that had it; an open PR or a failed lookup is silent. A snapshot taken while `activeOperation()` is non-nil and the view is empty is `unsettled`: `sync` briefly checks out the base commit, which would otherwise make every PR vanish and return as "Now watching"; the loop ignores it.) A foreground loop around the same live lookup `status` uses (`fetchPRInfos` + `classifyPR`, no cache; the CI progress count `status` appends to the Status word, `github.CIProgress`, is display only and not part of the marker, so a count changing is never an event), so it is exactly as fresh as `status` and reports errors the same way. Each cycle builds the very view `status` prints (`buildStatusView`, shared with `status`: read-only for `watch`, no index refresh and no save, and one lookup per cycle feeding both the displayed rows and the per-PR markers), and takes the PRs from it, each with its GitHub-derived marker; the table shows everything `status` shows (sub-commits, untracked and Ready commits, the local Syncing and Unsynced markers), but only the GitHub-derived markers are diffed, so the local ones never notify. The snapshot's PRs are carries forward the last known marker for a PR whose lookup failed (`carryForward`, so a failed lookup is never an event), and diffs against the previous snapshot (`diffWatch`): only PRs present in both with different markers are events, and a PR seen for the first time is only announced. `eventKind` maps a transition to the `GIT_SD_EVENT` value (CI running leaving to a non-failing state is `ci-passed`). Every message identifies the PR the way a person would (`eventMessage`: its Stack Set, its 1-based position among that set's groups in stack order, its number and title, e.g. `CI passed on PR 3 of 5 in feat-a (#120), now Approved: Add retry logic`), computed from the same group order `status` shows; `eventTitle` is the short form for a notification title. The wait between cycles is `nextWatchInterval`: the minimum after the baseline and after any change, otherwise doubled up to the maximum, with a 20 s ceiling while any PR is `CI running` (the one state that changes within seconds; review states are human-paced, so they only get the slow cadence). Sleeping compares wall-clock time once a second, and each of those ticks also rewrites the footer's "next check in" in place (`\r` and clear-line, via `watcher.countdown`; the footer is printed without a trailing newline so it can be rewritten, and the stop path adds the newline), so the countdown is live without redrawing the screen; so after a laptop wakes the next poll is immediate instead of up to a full interval late. Metadata is loaded and never saved, so the watcher cannot overwrite what a concurrent `sync` records. Outage handling: the first snapshot's errors are fatal, later ones are counted, three in a row announce an outage once (an `offline` notification) and a recovery is announced once. Notifications run `sd.watch.notify-command` through `sh -c` with a 10 s timeout and the `GIT_SD_*` environment; the loop's clock, sleeper, snapshot source and command runner are injectable so the whole loop is unit-tested without GitHub or real time. At the slowest cadence it costs about one GraphQL point per PR-batch per minute; one `gh` call per PR per cycle is the known inefficiency (a single batched query would be cheaper for long runs).
- **Sync output and exit status:** `sync` prints only outcomes, never its internal passes: the per-PR summary (`formatSyncSummary`), a `Deleted <n> finished branch(es).` count (per-branch lines only as `Warning:` when a deletion is skipped or fails), the dissolved Stack Sets, and a closing line. Every error goes through `reportSyncError` (`Error: could not <action>: <reason>`), which counts it: a failed group or step never stops the run (one bad PR must not block the others, and the next sync retries it), but the closing line then reads `Sync completed with <n> error(s).` and the process exits 1 so scripts and agents can tell. Warnings (branch kept, check failed, could not record what was synced) are retried automatically and leave the exit status alone. Errors that make continuing pointless (no `gh`, no metadata, no base branch, an authentication failure) still exit 1 immediately.
- **PR edits and the sync summary:** `sync` records `last_synced` on each top-level commit: a fingerprint of the PR title, body and base as last successfully applied to GitHub (set after a create or `gh pr edit`, so a failed edit is retried next sync; empty for PRs created before this existed, whose first sync edits once and records it). `gh pr edit` runs only when the fingerprint differs. `github.PushBranch` reports whether the push changed anything (git prints `Everything up-to-date` when it did not). A PR is summarised as *created* if `CreatePR` ran, *updated* if its branch was pushed with changes or it was edited, and *unchanged* otherwise. `gh pr edit` is therefore called only when the fingerprint differs, and an unchanged PR needs no push because its branch is rebuilt bit-for-bit (see "Trailer transparency").
- **Batched pushes:** `sync` pushes every branch it rebuilt in ONE `git push --porcelain --force <remote> <sha>:refs/heads/<branch> ...` (`github.PushBranches`) instead of one push per PR, because each push costs a full connection round trip (~1.1-1.35 s on the Pi even when nothing changed). Pass 1 therefore works in waves: (1) plan, in stack order, skipping merged/closed groups and building each remaining group's trailer-stripped chain locally on the previous group's tip; (2) one batched push; (3) in stack order, per group, advance the chain and edit its existing PR; PRs that do not exist yet are then created **concurrently** (at most `maxConcurrentPRCreates`, 4), because `gh pr create` takes ~2.2 s and GitHub handles concurrent creates in parallel (measured: 4 creates 8.2-9.1 s one at a time, 2.2-3.7 s together). Each new PR's base is the previous group's branch, which is already pushed, so creation order doesn't matter; the stack is registered from an explicit ordered PR list, so PR numbers need not follow stack order either. Results are applied and printed in stack order. `--porcelain` reports each ref's outcome (`=` up to date, `!` rejected, anything else updated), which gives `pushed` per branch and lets one rejected ref fail only its own group. A group whose push was rejected drops out; the later groups of the *same* Stack Set were built on its branch, so they are re-planned from the last good tip in a further wave (other sets are unaffected), which keeps the result identical to handling the groups one at a time. A failed PR *create* is different: the branch is already pushed and later groups already sit on it, so they keep their PRs (based on that branch) and the failed group is simply left without a PR and reported; the next sync creates it, and Stack registration for the set may report an error until then. `sync` says so: each failure prints `Error creating PR for branch <branch>: <error>`, followed by one line naming every branch left without a PR and telling the user to fix the error and re-run `git sd sync`. A failure of the whole push (no connection, bad credentials) fails every branch in the batch with git's message. In the common case there is a single wave and a single push. **Exception: a retarget.** If any existing PR's base on GitHub (`baseRefName`, already fetched by the prefetch) differs from the base the new chain gives it (a reorder, an insert or a removal), the wave pushes and retargets one group at a time as before. Pushing everything first is unsafe there: after a reorder, a PR's new head can be an ancestor of its *old* base branch, and GitHub then marks that PR merged (seen in `TestSDMoveReorderWithinSetPreservesPRIdentityAndApproval`, where the final `rebase` found a PR merged on GitHub whose merge commit was not on the base branch). Pushing a group and retargeting its PR before the next branch moves avoids that, which is why the original per-group order is kept for that case.
- **Fewer `gh` round trips:** `sync` and `rebase` need each group's PR state (merged/closed/open) before they act, and used to ask GitHub one PR at a time. They now look every PR up concurrently up front (`fetchPRStates` in `cmd/git-sd/prefetch.go`, the same bounded pool `status` uses, `maxConcurrentPRLookups`), then read the results in stack order, so decisions, warnings and errors are unchanged and a stack costs about one round trip instead of one per PR. A failed lookup is kept per PR and handled where it was before (an environment error aborts, any other failure is handled for that PR alone). `github.CreatePR` no longer follows `gh pr create` with a `gh pr view`: `create` prints the new PR's URL, the number is its `/pull/<n>` suffix and a new PR is OPEN; the lookup remains only as a fallback when the output has no recognisable URL and for the 'already exists' path.
- **Trailer transparency:** the `git-sd-id` trailer never reaches GitHub. Before pushing a group's branch, each commit is copied via a cherry-pick pass (`git.BuildTrailerStrippedChain`, the same skeleton as `SquashCommitsOntoBase`) that drops the `git-sd-id:` line from the message. Each copy is written with `git commit-tree` (no hooks run) using the original commit's author and committer name/email, and its **author date as both dates** (like `rebase --committer-date-is-author-date`); the message goes through `git stripspace`, matching `commit -m`'s cleanup. Author dates survive git-sd's own local rewrites (`move`/`rebase`/`fixup` cherry-picks) and `--amend`, while committer dates don't — so an unchanged group on an unchanged base is rebuilt bit-for-bit, and `sync`'s force-push of it is a no-op on GitHub (no timeline/CI churn). A real change — content, message, author, or a new base after a lower PR lands — still produces new SHAs and is pushed. `git-sd-id` remains purely local bookkeeping in `metadata.json` — only its presence in the *pushed* copy of the commit changed.
- **Branch naming:** branch names are a slug of the commit's subject line (lowercase; runs of non-`[a-z0-9]` characters collapsed to a single `-`; trimmed; truncated to roughly 45 characters at a `-` boundary) plus a short suffix from the group's `git-sd-id` for collision-safety and traceability, e.g. `fix-bug-check-nil-a1b2c` (`git.BranchNameSlug`). The slug is computed once, at first sync, and stored in `metadata.Commits[id].BranchName` — never recomputed on a later message edit. If the subject line slugifies to empty (e.g. pure emoji or non-Latin script), the `git-sd-id` itself is used as the branch name. The PR title is still set directly from the real, unmodified commit subject line on every sync — it does not need to be recovered from the branch name. `sd.pr.branch-name-format` was removed; the scheme is no longer configurable.
- **PR body / "Stack" table:** git-sd's own stack-table generation and the "don't merge from the GitHub UI" warning were dropped. GitHub's native Stacks UI renders stack navigation outside PR-body content, and the UI-merge warning is moot once merging — whether via `git sd merge`, `gh stack merge`, or the GitHub web UI directly — retargets the rest of the stack natively.
- **Approval/CI safeguards:** git-sd's own pre-merge `GetDetailedPRInfo` check (and the `GIT_SD_SKIP_SAFEGUARDS` escape hatch) were removed. Enforcement is now whatever branch protection is configured on the base branch — a repo with no branch protection configured has nothing blocking an unapproved/CI-red merge.
- **Merge granularity:** `git sd merge <set> --upto <index>` now leaves one commit per PR on the base branch (native cascading merge) instead of one squashed commit for the whole prefix, and there are no more "superseded" PRs to close/comment on — every PR in the merged range merges as itself.

### What doesn't change
- The single linear working branch / commit-trailer editing model (`assign`, `move`, `fixup`, `status`).
- `GroupCommits`/`PRGroup` grouping logic (`cmd/git-sd/groups.go`).
- Local post-merge reconciliation of the user's own working branch (`rebase`'s rebuild) — GitHub's Stacks feature only knows about the synthetic branches it's given; `merge` still strips merged commits back out of the user's real working branch after a merge (now via `rebaseOnto`, shared with `git sd rebase`).
- `--upto <index>` semantics for partial/bottom-prefix merges — matches `gh stack merge <PR>`'s native "merge up to and including" behavior directly, so the flag's contract carries over unchanged.

### Dependencies & risk
- Requires the `gh` CLI authenticated against a repo with Stacked Pull Requests access; all Stacks/async-merge calls go through `gh api`, not the `gh-stack` extension.
- GitHub's Stacked Pull Requests feature is in **public preview** (shipped 2026-07-30) and explicitly "subject to change." The design above was validated hands-on against the sacrificial repo as of 2026-07-31/2026-08-04, but a preview API can change shape before GA — there is intentionally no legacy fallback path in the code if it does.
- No migration path exists for stacks created under the pre-migration `sd/{user}/{stack-set-name}/{git-sd-id}` branch/PR scheme: merge or close any in-progress stack before upgrading past this change.
