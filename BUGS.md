# git-sd Bug Ledger (BUGS.md)

This file tracks implementation bugs and anomalies discovered during automated validation.

## Status Legend
- **OPEN:** Issue identified, awaiting fix.
- **FIXED:** Autonomous or manual fix applied and verified.
- **AMBIGUOUS:** Identified behavior requiring human confirmation to proceed.
- **DISMISSED:** Human confirmed the behavior is intended or out of scope.

| B-014 | Med | FIXED | OBVIOUS | `git sd merge` treats a transient "Pull Request is not mergeable" as terminal. | B-017 | Med | FIXED | OBVIOUS | External user report (`GIT-SD-BUG.md`): `git sd sync <stack>` fails with a cherry-pick conflict when a Stack Set's commit content depends on a *different*, already-synced-but-unmerged Stack Set — e.g. commit B's parent is commit A, A is assigned to Stack Set `sentinel-dir-rename` (already pushed/PR'd), B is assigned to a brand-new Stack Set `events-dir-rename`. `sync` builds each Stack Set's push chain from only its own commits on top of `since` (`BuildTrailerStrippedChain`), by design — the same path locked in by `TestSDSyncDetectsConflictFromInterleavedStackSet` for two genuinely *unrelated* interleaved stacks that shouldn't silently absorb each other's changes. The reporter's case was different in intent (a genuine, deliberate stack-of-stacks), but git-sd's model has no "Stack Set B is based on Stack Set A" concept — decided (with user) not to add one: dependent commits belong in the same Stack Set, so this is user error under the current model, but the tool gave no warning until a confusing `sync`-time conflict (and even then printed "Sync completed." and exited 0 regardless — see the open follow-up item in `GIT-SD-BUG.md` about `sync`'s own exit-code/messaging bug, not fixed here). | FIXED (preventively, not by changing `sync`): added `git.SimulateChainBuild` (`internal/git/git.go`), which replays a Stack Set's own commits via successive `git merge-tree --write-tree --merge-base=<commit>^ <tree> <commit>` calls — pure plumbing, no checkout, no working-tree/index mutation, ~20ms/commit — exactly modeling what `BuildTrailerStrippedChain` will do at sync time. `assign.go` now validates every touched Stack Set with it before saving; on failure the whole argument's tentative changes are rolled back (metadata untouched), a clear error names the Stack Set the commit likely depends on, and the process exits non-zero (this also gave the pre-existing out-of-range-index case real exit-code discipline for the first time, since it's the same code path). Deliberately validates the *whole* chain of a Stack Set's own commits, not each commit in isolation against `since` — an isolated-per-commit check was tried first and found to false-positive on the ordinary case of assigning several mutually-dependent commits to the *same* Stack Set together (e.g. `assign feat-a:0-2`), which `sync` already handles correctly by chaining within a set.
